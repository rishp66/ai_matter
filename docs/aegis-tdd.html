01

Overview & goals

AEGIS turns a Mattermost account into a personal agent. Incoming messages are routed through a GraphN workflow that retrieves the user's context and produces a reply. The agent then does one of two things, with no per-message configuration from the user:

AUTO-SEND

The reply was composed using public context only. Low friction, no interruption — it goes out immediately.

DRAFT + HOLD

Composing the reply required private context. The agent drafts and holds for the user's explicit approval before anything leaves.

◆ North star

Maximize auto-send while never auto-sending anything that touched private context. That asymmetry is the whole product. The fail-safe is always DRAFT — never SEND. Every ambiguous case, low-confidence retrieval, or unexpected state resolves to a held draft.

Goals

  • Seamless transition. The user never picks "public" or "private" per message. The system decides from what the reply was actually built on, and only interrupts when private information would otherwise leak.
  • Safe by construction, not by classifier. The auto-send path must be incapable of leaking private data — not merely unlikely to. (See §04.)
  • Explainable holds. When a draft is held, the user sees why — e.g. "referenced 2 private sources."
  • Loop-proof. Two agents must never talk each other into an infinite exchange. (See §06.)

Non-goals (MVP)

  • Multi-tenant onboarding, RBAC, or polished KB-management UI.
  • True user impersonation — the MVP posts as a clearly-labeled bot "on behalf of {user}" (see §09).
  • Open Claw as a second runtime. GraphN is the single backend for the MVP — it gives more specific, deployable control over the workflow.
  • Mobile, federation, audit-log persistence.

System architecture

Three moving parts. The fork owns the surface the user sees and the login hook; GraphN owns the brains; a thin bridge service glues them and is where most hackathon code lives.

Components

Forked MattermostUI surface (draft card, drafts inbox, public/private settings), login hook, bot identity, custom REST endpointsMedium — isolated aegis/ package + webapp components
BridgeSubscribes to WebSocket post events, calls the GraphN gateway, applies the gate verdict, posts replies or draft cards, handles button callbacks, holds loop countersHigh — most logic lives here

▸ Decision — keep orchestration in the bridge, not the fork

The fork carries UI + thin hooks/endpoints; all GraphN-calling and gate logic lives in a separate bridge service. This keeps fork changes minimal (less merge debt), lets the team write the bridge in any language and iterate fast, and gives a single, instrumented choke point for every private-data access. Overrule if you'd rather embed it in the Go server.

03

Context model

Context is split into two GraphN knowledge bases rather than one KB with per-chunk tags. Two physically separate stores make provenance trivial: "did the reply touch kb-private?" is a yes/no fact about which store was queried, not an inference about a label.

kb-public

User-determined sources the agent may share without asking: public channels, published docs, FAQ-style notes, anything the user has marked shareable. Grounding a reply only here is what earns AUTO-SEND.

kb-private

The user's own private data: private notes, DMs, internal docs. Reachable only through a gated escalation step. Any retrieval from here forces DRAFT — no exceptions.

Loaded on login

The diagram's "loads context on login" arrow maps to the Mattermost server UserHasLoggedIn hook. On login the forked server notifies the bridge, which warms / scopes the user's two KB namespaces in GraphN and opens a session that maps Mattermost user → GraphN workspace + KB namespaces + secrets.

"User Determined" tagging

A settings surface in the fork's webapp lets the user assign sources/channels/notes to public or private, which populates the two KBs. Default everything to private until explicitly marked public — this makes mislabeling fail safe (an unmarked source is held, never auto-sent).

04

The context gate — hard problem #1

The diagram's open question — "how do we identify which context we're using?" — is answered with retrieval provenance, not an LLM classifier. We don't ask a model to judge whether its own answer is "safe." We observe what the workflow actually grounded on and decide deterministically.

Public-first, escalate-and-lock

The key move: structure the workflow so the auto-send path never even loads private context. Then auto-send is safe by construction, not by trust.

  1. Public-only compose. Attempt to answer using kb-public and public tools only. The private KB is not in this context window at all.
  2. Sufficient? If the public-only attempt grounds a confident answer → verdict AUTO_SEND.
  3. Escalate & lock. If it's insufficient, escalate to a second compose that may query kb-private — and the verdict is now permanently DRAFT, regardless of how the model uses what it retrieved. Retrieval, not usage, is the trigger.
  4. Abstain → DRAFT. Low-confidence / retriever abstains / ambiguous → DRAFT (fail-safe).

Why provenance beats a classifier

A classifier has a nonzero false-positive rate, and the one error AEGIS cannot tolerate is a false AUTO_SEND — auto-sending a reply that leaked private data. Provenance has no false AUTO_SEND by construction: if the private store was queried, that's a recorded fact, and the verdict is DRAFT. The composition model never gets a vote on whether to send.

⚠ The subtle trap — and the fix

A model could paraphrase private info it merely saw in-context even if "retrieval" didn't formally fire. The escalate-and-lock structure closes this: the auto-send compose never has kb-private in its window, and the moment we open the private store we've already committed to DRAFT. There is no path where private content reaches an auto-sent message.

▸ Decision — one instrumented choke point for private access

Every route to private data (the private KB, any private/side-effecting MCP tool) must pass through the bridge's gated escalation. No ungated private source may exist. If it isn't reachable through the instrumented path, provenance can't see it — so it must not exist.

05

Approval UX

A held draft surfaces to the user as a card — implemented with a Mattermost custom post type rendered by the forked webapp, with interactive message-attachment actions as the action backbone. The bot posts it in a DM / thread to the user, never in the target channel.

Card anatomy

  • Destination — where this would go (channel / recipient + the originating thread).
  • Trigger — the incoming message that prompted the reply.
  • Proposed reply — the drafted text.
  • Provenance line — the explainability: Held · referenced 2 private sources or Held · low confidence.
  • Actions — Approve · Edit · Discard.

Action mechanics

Each button's integration.url points at a bridge endpoint, with state carried in the action context (draft id, target channel, root thread). On click:

  • Approve → bridge posts the reply to the target thread, then updates the card to a terminal "Sent" state with no buttons.
  • Edit → opens an interactive dialog prefilled with the draft; submit re-posts the edited card or sends. stretch
  • Discard → bridge drops the draft and updates the card to "Discarded."
⚠ Known Mattermost quirk

Updating an interactive post can drop its action buttons. That's fine here — every action resolves the card to a terminal, button-less state (Sent / Discarded), so we never need to keep buttons alive across an update.

06

Loop prevention — hard problem #2

The diagram's *CONCERN* — two agents conversing in a loop. A loop requires two agents auto-sending at each other, so breaking the auto-send link breaks the loop. Three layers, cheapest first:

Layer 1 — bot guard required

If an inbound post is bot-originated (props.from_bot === "true" or sender in a known-bot set), the verdict is forced to DRAFT — never auto-send to a bot. This alone breaks the loop, since a loop needs two agents auto-sending.

Layer 2 — thread depth counter required

Per root-thread counter of consecutive bot turns with no human post between them. Halt at N = 3: stop responding and post an ephemeral "paused — human turn needed." A human message resets the counter.

Layer 3 — similarity break stretch

If the last K bot replies in a thread exceed cosine similarity τ, halt — catches degenerate "you're welcome / no, thank you" repeats that slip past depth limits.

Counters key on the root post id and live in the bridge — in-memory for the MVP, Redis after. Layer 1 is the load-bearing rule; Layers 2–3 are belt-and-suspenders.

07

The fork

▸ Decision — fork, not plugin

We fork to fine-tune functionality: full control of post rendering, the drafts inbox, and the context-settings surface, without fighting plugin boundaries. The trade is merge debt against upstream — accepted for a hackathon and contained by the discipline below.

What changes

LayerChange
webapp · React/ReduxCustom post-type renderer for the draft card; a "Drafts" inbox view; a Public/Private context settings page.
server · GoUserHasLoggedIn hook → notify bridge; custom endpoints (/aegis/approve, /aegis/edit, /aegis/discard); bot account provisioning.
integration primitivesUnchanged — we still use the bot, WebSocket events, and attachment actions. The fork adds UI on top of these, it doesn't replace them.
⚠ Fork discipline (keeps merge debt survivable)

Isolate all server changes behind an aegis/ package and a feature flag. Keep a clean rebase branch against a pinned upstream tag. Touch as few core files as possible — orchestration lives in the bridge precisely so the fork stays thin.

09

Risks & open questions

Risks

● Prompt injection via the incoming message

A hostile message could instruct the agent to fetch and reveal private data. Mitigation is structural: kb-private is reachable only through the gated escalation that forces DRAFT, and the auto-send window never contains private content. Treat message text as data, not instructions, in the compose prompt.

● Provenance completeness

If any private data source exists outside the instrumented path, provenance can't see it and the guarantee breaks. Enforce the single choke point (§04) — no ungated private sources.

  • Mislabeled context. Default-private + fail-safe DRAFT means a mislabel holds rather than leaks.
  • Latency. Gateway round-trip + retrieval may dull the "real-time" feel. Acceptable for MVP; show a typing indicator.
  • Bot-detection reliability. Combine the from_bot prop with a known-bot allowlist; default unknown automation to DRAFT.
  • Fork merge debt. Contained by isolation + feature flag + thin changes (§07).

Open questions

▸ Identity — who does the agent post as?

The model is "agent acts as the user," but true impersonation is harder and riskier. MVP recommendation: post as a dedicated bot clearly labeled "on behalf of {user}." Posting as the user is post-MVP. Confirm this is acceptable for the demo.

  • Reply destination — MVP replies in the same thread the message arrived in. New-DM routing is later.
  • Counter persistence — in-memory for the hackathon; Redis when multi-process.
  • Confidence threshold — what retrieval score trips "abstain → DRAFT"? Tune on the demo corpus during P2.

A · Gate verdict (bridge, public-first / escalate-and-lock)

bridge/gate.py
# The auto-send path never loads kb-private. Retrieval — not usage — sets the verdict.
def decide(msg, session):
    # Layer 1: a loop needs two agents auto-sending. Bot origin can never auto-send.
    if msg.is_from_bot or msg.sender_id in KNOWN_BOTS:
        return Verdict(DRAFT, reason="bot origin")

    # Pass 1 — compose using ONLY public context. kb-private is not in this window.
    pub = graphn.run(WORKFLOW_PUBLIC, input=msg.text, kb=["kb-public"])

    if pub.grounded and pub.confidence >= CONF_MIN:
        return Verdict(AUTO_SEND, reply=pub.text, provenance=pub.sources)

    # Pass 2 — escalate to private. The verdict is now LOCKED to DRAFT no matter what.
    priv = graphn.run(WORKFLOW_PRIVATE, input=msg.text, kb=["kb-public", "kb-private"])
    return Verdict(DRAFT, reply=priv.text,
                   reason=f"referenced {priv.private_hits} private sources")
